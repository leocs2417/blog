Agent 开发完成并不意味着工作结束。真正进入用户场景之后，问题往往才开始暴露：有时答非所问，有时检索不到正确资料，有时明明有工具却不会调用；有时工具调用参数错误，有时任务陷入循环；有时回答质量不错，但响应太慢、成本太高；还有一些问题只会在真实用户、真实数据和复杂上下文中出现。

这些问题很容易被简单归因于“Prompt 写得不够好”或“模型能力不够强”。但 Agent 是由模型、指令、上下文、检索、工具、状态、编排和业务系统共同组成的应用。**最终表现是整个系统的结果，调优也必须从系统层面入手。**

这篇文章想总结的是一套持续优化方法：如何识别 Agent 的问题、定位问题发生在哪一层、设计可验证的改进方案，并通过数据确认优化是否真正有效。

---

## 1. 先建立正确认知：Agent 调优不是只改 Prompt

传统软件系统通常有相对确定的输入、逻辑和输出。Agent 则存在概率性行为：同一个问题可能产生不同措辞、选择不同执行路径，甚至在某些边界条件下出现不同结果。

因此，Agent 的质量不能只通过几条手工对话来判断，更不能在没有数据的情况下连续修改 Prompt，直到“感觉变好了”为止。

一个 Agent 的表现通常受到以下因素共同影响：

```text
模型能力与模型配置
        |
        v
系统指令 / Prompt / 策略
        |
        v
上下文组装 / 会话 / 记忆
        |
        v
检索 / RAG / 外部数据
        |
        v
工具定义 / 参数 / 执行结果
        |
        v
Agent Loop / 状态 / 编排 / 停止条件
        |
        v
业务权限 / Guardrails / 应用逻辑
        |
        v
最终回答与实际任务结果
```

如果最终答案错误，原因可能是模型理解错误，也可能是检索结果错误、工具返回了过期数据、权限过滤遗漏，或者业务代码将结果错误地传给了模型。

所以，调优的第一原则是：**先定位问题，再选择优化手段；不要把所有问题都交给 Prompt。**

## 2. 先看见问题：建立 Agent 的可观测性

没有运行过程记录，Agent 出错之后就只能猜测。对真实应用来说，Trace 应该是调试 Agent 的基础设施，而不是等用户反馈很多问题后再补。

### 2.1 一条有价值的 Agent Trace 应该记录什么？

建议将一次任务的执行过程关联起来，至少记录：

| 维度 | 建议记录的内容 |
| --- | --- |
| 请求信息 | request ID、conversation ID、user/tenant 标识（脱敏或匿名化） |
| 版本信息 | Agent 版本、Prompt 版本、工具 Schema 版本、模型及参数 |
| 模型调用 | 请求耗时、Token 使用、响应状态、结构化输出校验结果 |
| 检索过程 | 查询词、过滤条件、候选文档 ID、相关性分数、最终选中的片段 |
| 工具调用 | 工具名称、参数摘要、权限检查、调用耗时、返回状态和错误码 |
| 执行状态 | 当前步骤、重试次数、停止原因、是否触发人工审批 |
| 最终结果 | 是否完成、业务结果、用户反馈或后续修正 |
| 成本与性能 | TTFT、端到端延迟、P50/P95、输入和输出 Token、费用估算 |

不要把所有原始用户数据、个人信息、访问令牌或敏感业务内容无差别写进日志。应根据排障需要做字段脱敏、访问控制、保留期限和采样策略。

同时，不要把模型的隐藏思维链当成必须采集的日志。工程上更有价值的是可观察的事件：输入与输出、工具选择、经过校验的参数、工具结果、状态变化、错误和明确的决策摘要。

OpenAI Agents SDK 提供了模型调用、工具调用、Handoff、Guardrail 和自定义步骤的 Trace；[OpenTelemetry GenAI Semantic Conventions](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/) 则有助于在不同模型和工具之间建立可关联的观测数据。

### 2.2 Trace、Log 和 Metric 的分工

- **Trace：** 还原一次任务完整经过了哪些步骤，适合分析“为什么失败”。
- **Log：** 记录特定事件和错误细节，适合排查具体代码和依赖问题。
- **Metric：** 统计一段时间内的成功率、错误率、延迟、成本和调用量，适合监控趋势和告警。

三者应该通过 request ID、trace ID、conversation ID 或 task ID 关联，而不是各自孤立。

## 3. 先定义质量，再谈优化：建立 Evaluation

“回答更好”“更聪明”不是可执行的优化目标。需要先明确 Agent 的质量维度，并为重要任务建立固定评测集。

### 3.1 Agent 应该评估哪些维度？

不同产品的权重不一样，但通常可以从以下方面考虑：

| 质量维度 | 需要回答的问题 | 常用评估方式 |
| --- | --- | --- |
| 任务完成率 | 用户真正要完成的事情是否完成？ | 规则校验、业务状态校验、人工评审 |
| 意图理解 | 是否正确理解用户的目标和约束？ | 标注数据集、分类准确率、LLM Judge |
| 回答质量 | 内容是否正确、完整、清晰且有帮助？ | 参考答案、评分 Rubric、人工评审 |
| Groundedness | 关键结论是否有可信来源支持？ | 引用检查、事实校验、LLM Judge |
| 检索质量 | 正确资料有没有被召回和排序？ | Recall@K、Precision@K、MRR、nDCG |
| 工具调用 | 是否选对工具，参数是否正确？ | 工具轨迹断言、Schema 校验、业务结果检查 |
| 安全与边界 | 是否遵守权限、拒绝和审批要求？ | 规则测试、对抗测试、人工评审 |
| 稳定性 | 多次运行是否保持合理一致？ | 重复运行、边界样本、线上异常监控 |
| 性能与成本 | 是否足够快，单次任务成本是否可接受？ | TTFT、P50/P95、Token、工具耗时和费用 |

不要把所有维度压成一个分数。比如答案正确率提高，但越权风险也上升，不能算真正的优化。建议将关键质量、安全、性能和成本指标分别跟踪。

### 3.2 建立自己的评测数据集

评测集应该来自真实任务，而不是只由开发者想象的理想输入组成。数据来源可以包括：

1. 产品需求和验收用例。
2. 开发阶段手工设计的典型任务。
3. 线上脱敏后的真实用户输入。
4. 用户纠正、投诉和人工接管记录。
5. 工具失败、检索失败和异常流程的 Trace。
6. 对抗性输入和边界条件。

每个样本最好包含：

```yaml
id: order-refund-001
category: tool-use
input: "帮我申请订单 A123 的退款，原因是商品破损"
context:
  user_id: test-user-01
  permissions:
    - order:read
    - refund:create
expected:
  must_call:
    - get_order
    - create_refund_application
  must_not:
    - execute_refund_payment
  final_output_checks:
    - mention_application_status
    - include_application_reference
risk_level: medium
```

这是示意结构，实际字段应根据项目的评测框架调整。重点是记录预期行为，而不仅是预期文字。Agent 任务经常存在多种合理表达，但工具选择、权限边界和业务结果通常可以更明确地检查。

### 3.3 规则评测与 LLM-as-a-Judge 配合使用

**能用确定性规则判断的，就不要完全依赖另一个模型来判断。**

- JSON Schema 是否通过：用代码校验。
- 是否调用了指定工具：检查 Trace。
- 是否创建了正确的业务记录：查询测试环境中的业务状态。
- 是否引用了正确文档：检查文档 ID 和引用片段。
- 语义是否完整、是否回答了用户核心诉求：可以使用 LLM-as-a-Judge 辅助评价，再用人工样本校准。

LLM Judge 本身也可能判断错误。应该给它清晰的评分标准、可用证据和边界案例，并定期抽样与人工标注结果比较。不要因为某个 Judge 给出了分数，就把它当成绝对真值。

### 3.4 离线评测与线上评测

- **离线评测：** 在固定数据集上比较 Prompt、模型、工具或检索配置的变化，适合上线前回归。
- **线上评测：** 从真实流量中抽样、监测和收集反馈，观察实际使用场景中的质量变化。
- **人工评审：** 对高风险任务、复杂语义和自动评分不稳定的场景进行人工复核。

一个常见闭环是：线上收集 Trace → 标记问题 → 转成评测样本 → 在离线环境中验证修复 → 小流量上线 → 继续观察线上表现。

OpenAI 的 [Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals) 建议先用 Trace 定位工作流问题，再逐步建立数据集和重复评测；LangSmith 也提供离线和线上评估流程。需要留意产品迁移信息：截至 **2026 年 11 月 23 日**，OpenAI 官方[旧版 Evals 页面](https://developers.openai.com/api/docs/guides/evals)标注该平台进入弃用阶段，原有 Evals 内容于 2026 年 10 月 31 日转为只读，并计划于 **2026 年 11 月 30 日**关闭。新项目不应把即将下线的旧版 Evals 平台当作长期评测架构的基础，应根据当前可用的 Datasets、Trace graders 和 SDK 工作流选择实现方式。

## 4. 建立问题分类：先定位是哪一层出了问题

建议把 Agent 的常见问题整理为一个 Failure Taxonomy。每次线上故障或评测失败，都尽量归入明确类别，而不是简单记录“模型答错了”。

| 问题类别 | 常见症状 | 优先检查 |
| --- | --- | --- |
| 意图理解 | 把查询当成操作、忽略用户限制 | 输入、分类和路由结果 |
| 指令遵循 | 忽略关键约束、输出格式不稳定 | Prompt 结构、规则冲突和上下文 |
| 知识与事实 | 幻觉、过时信息、引用不准确 | 数据源、检索、来源版本和 Grounding |
| RAG 检索 | 找不到资料、召回噪声太多 | Chunk、Embedding、过滤、排序和 Query |
| 工具选择 | 有工具却不用，或选错工具 | 工具描述、工具列表和路由条件 |
| 工具参数 | 参数缺失、格式错误、目标对象错误 | Schema、参数上下文和服务端校验 |
| 执行流程 | 重复调用、无限循环、提前结束 | 状态管理、停止条件和步骤预算 |
| 记忆与上下文 | 忘记前文、记错用户偏好、上下文污染 | 历史摘要、记忆写入和检索策略 |
| 稳定性 | 超时、重复执行、任务中断 | 重试、幂等、持久化和恢复 |
| 性能与成本 | 响应慢、Token 高、工具调用过多 | 延迟分解、上下文大小和执行链路 |
| 安全 | 越权、Prompt Injection、危险操作 | 权限、可信边界和人工审批 |

问题分类不是为了增加管理流程，而是为了让优化动作更有针对性。

## 5. 常见问题与优化方法

### 5.1 回答不准确、答非所问

**可能原因：**

- 用户意图理解错误。
- Prompt 目标模糊或规则相互冲突。
- 上下文中缺少关键事实。
- 检索结果不相关或已经过期。
- 模型在缺少证据时仍然猜测。

**优化方向：**

1. 先判断是意图识别、知识缺失还是表达问题，不要直接重写整份 Prompt。
2. 用真实失败案例补充输入样本，覆盖简称、错别字、模糊表达、多轮追问和多目标请求。
3. 明确关键定义、业务规则、回答格式和拒答条件。
4. 要求关键事实尽量引用来源；当没有足够依据时，允许 Agent 表示不知道或请求补充信息。
5. 对必须稳定的分类和字段提取，考虑结构化输出或代码校验。

不要把“回答必须完整”误写成“无论如何都必须给出答案”。在证据不足时澄清或拒绝，往往比编造更可靠。

### 5.2 RAG 检索不到正确资料，或答案没有依据

RAG 问题至少要拆成“是否找得到”和“找到后是否用对”两部分。

**第一步：检查数据质量。**

- 文档是否完整解析？表格、标题、图片和附件内容有没有丢失？
- 文档有没有版本、更新时间、权限和来源元数据？
- Chunk 是否太大或太小？是否把标题和正文拆开？
- 文档更新和删除后，索引是否同步？

**第二步：检查召回质量。**

- Query 是否表达了用户真正要查的内容？
- 是否需要 Query Rewrite 或扩展关键词？
- 纯向量检索是否会漏掉编号、名称和专有词？
- 是否应该采用关键词 + 向量的 Hybrid Search？
- Top-K 是否合适？是否需要 Reranker？
- 权限过滤是否在检索前或检索过程中正确执行？

**第三步：检查生成过程。**

- 检索内容是否真正进入了模型上下文？
- 模型是否区分资料中的事实、推断和不确定内容？
- 是否保留来源 ID 和引用信息？
- 多份资料冲突时，是否有时间、版本或权威性规则？

可使用 Recall@K 衡量相关资料是否被召回，Precision@K 衡量召回结果中有多少真正相关，MRR / nDCG 衡量排序质量；最终答案还需要检查 Groundedness 和引用正确性。

优化时应使用固定查询集同时比较各阶段结果，否则很容易出现“某几个问题答对了，但整体召回退化”的情况。

### 5.3 工具调用不正确

工具调用失败经常被误以为是模型不够聪明，实际上 Tool Schema 和工具设计本身可能存在问题。

常见原因：

- 工具命名模糊，多个工具职责重叠。
- 描述没有说明何时使用、何时不使用。
- 参数类型、枚举和必填字段定义不清楚。
- 工具返回值过长、没有结构化错误信息。
- 一次暴露太多工具，增加选择难度。
- 模型可以调用工具，但应用没有做好权限和参数校验。

优化建议：

1. 一个工具只承担一个清晰职责，命名使用明确动作和业务对象。
2. 使用严格的输入 Schema，明确必填字段、枚举和字段含义。
3. 为工具提供简短、可区分的描述，并补充必要的调用示例。
4. 让工具返回结构化结果，包括成功状态、业务数据、错误类型和是否可重试。
5. 按 Agent 的任务和权限动态提供最小工具集，避免把所有工具一次性暴露。
6. 服务端再次校验用户身份、资源归属、参数和操作风险。
7. 对写操作设计确认、幂等和审计机制。

如果工具调用的正确性可以由代码直接判断，就应将工具选择和参数检查加入自动评测，而不是只看最终回答。

### 5.4 Agent 执行重复、陷入循环或过早结束

常见表现：同一工具反复调用、反复查询相同数据、执行很多无意义步骤，或者工具还没有真正完成任务就输出“已完成”。

**优先排查：**

- 是否有明确的停止条件？
- 是否设置最大步骤数、最大工具调用数、超时和 Token 预算？
- 工具错误是否被正确区分，还是每种错误都被当成可重试？
- 工具返回的信息是否足够让模型判断下一步？
- 当前任务是否本来就适合用确定性 Workflow？

**优化方式：**

- 为每类任务定义可验证的完成条件，而不是依赖模型主观判断“看起来做完了”。
- 为重复调用设置检测机制和执行上限。
- 将稳定流程改成代码编排，只把动态决策交给模型。
- 对长任务持久化关键状态，让任务中断后可以恢复。
- 对失败设置有限重试，超过阈值后转人工或明确返回失败。
- 工具操作需要幂等，避免重复执行造成真实业务影响。

Agent 应该有自主决策空间，但自主不等于没有边界。

### 5.5 多轮对话丢失上下文，或记忆出现错误

记忆不是把全部历史消息无限拼接到 Prompt 里。随着对话增加，历史会越来越长，噪声也会越来越多。

建议先区分三类信息：

| 类型 | 内容 | 适合的管理方式 |
| --- | --- | --- |
| 当前任务状态 | 正在执行什么、已完成哪些步骤、下一步是什么 | 服务端 State / Checkpoint |
| 会话短期上下文 | 当前会话中的必要对话和事实 | 最近消息 + 摘要 + 按需检索 |
| 跨会话长期记忆 | 稳定偏好、用户明确要求保存的事实 | 有来源、时间和管理入口的持久化记忆 |

优化重点：

- 只保留对当前任务有帮助的信息，不要默认把所有历史放进模型上下文。
- 摘要要保留事实、决策、约束和未完成任务，避免只保留聊天概述。
- 长期记忆设置写入规则，区分用户明确提供的事实和模型推断。
- 对过时、冲突或不确定的记忆设计更新、确认和删除机制。
- 记忆检索应有用户隔离和权限过滤。
- 重要的执行状态应保存在应用服务中，不要只依赖模型“记得”。

Anthropic 在 2026 年的 [Context Engineering 讨论](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools) 中强调了 Memory、Compaction 和 Tool Clearing 等上下文管理方式。核心启发是：上下文不是越长越好，应该保留当前任务真正需要的信息。

### 5.6 Agent 不遵守约束，甚至受到外部内容诱导

这类问题不能只靠“在 Prompt 最后再强调一次”解决。

首先要区分不同层级的规则：

- 系统和开发者设定的产品策略。
- 当前用户请求和授权范围。
- 工具返回的外部数据。
- 文档、网页和邮件等不可信内容。

外部数据可能包含恶意指令，不能因为它被检索到或由工具返回，就获得更高的指令权限。尤其不能允许一段文档内容指示 Agent 导出密钥、扩大权限或执行危险操作。

建议组合使用：

1. 工具最小权限和明确的读写分离。
2. 服务端鉴权和资源级授权。
3. 对高风险操作增加人工确认。
4. 结构化输出、参数白名单和业务校验。
5. 对外部内容做不可信数据处理，不让其覆盖系统策略。
6. 对 Prompt Injection、越权访问和恶意工具结果进行对抗测试。
7. 对敏感数据进行最小化传递和脱敏。

参考 [OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-2026/) 和 [MCP Authorization / Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)。

### 5.7 响应慢、Token 消耗高、运行成本不可控

性能优化前，先把端到端耗时拆开：

```text
用户发起请求
  -> 应用鉴权与上下文加载
  -> 检索
  -> 模型调用 1
  -> 工具调用 1
  -> 模型调用 2
  -> 工具调用 2
  -> 最终生成
  -> 前端渲染
```

每一段都应该能测量。模型不是唯一的耗时来源，外部 API、向量检索、串行工具调用和前端等待也可能占据大量时间。

建议监控：

- TTFT（Time To First Token）：用户开始请求到首个文本片段的时间。
- End-to-end latency：从用户操作到任务完成的总耗时。
- P50 / P95：分别观察典型体验与长尾体验。
- 输入、缓存输入和输出 Token。
- 每次任务的模型调用次数、工具调用次数和成本。
- 重试、失败、降级和人工接管的比例。

常见优化手段：

1. **模型路由：** 简单分类、提取和格式化任务不一定需要最强模型；复杂规划和高风险任务再使用更强模型。前提是用评测集验证质量不退化。
2. **缩短上下文：** 过滤低相关资料、清理重复内容、限制历史窗口，只传递当前任务所需信息。
3. **减少串行请求：** 彼此独立的只读查询可以并行执行；有依赖关系的操作必须按顺序执行。
4. **缓存：** 对稳定且可复用的检索结果、只读数据和提示词前缀评估缓存收益，同时明确失效策略。
5. **减少无效工具调用：** 改善工具描述、路由和执行状态，不让 Agent 为了确认同一件事反复调用工具。
6. **流式响应：** 在适合的场景尽早向用户反馈进度，但要清楚区分“正在执行”和“已经完成”。
7. **设置预算：** 为任务设定 Token、模型调用、工具调用、时间和费用上限。

OpenAI 的 [Latency Optimization](https://developers.openai.com/api/docs/guides/latency-optimization) 将减少输入、减少请求、并行化和降低不必要的模型使用列为重要方向；[Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching) 也可以在适用场景降低重复前缀的成本和延迟。缓存不是通用答案，必须结合数据新鲜度和安全边界设计。

### 5.8 模型表现不稳定或升级后效果退化

模型升级、供应商切换、推理参数变化，可能导致工具选择、回答风格和任务成功率发生变化。

建议：

- 保留固定评测集，比较新旧模型在同一批任务上的表现。
- 不只比较平均分，也检查失败案例、长尾输入和高风险样本。
- 按任务类型选择模型，而不是全站固定一个模型或盲目使用最大模型。
- 记录模型 ID、参数、Prompt 版本和工具 Schema 版本。
- 对模型或供应商切换进行灰度验证，并保留回滚能力。
- 对结构化结果做 Schema 校验，对关键业务动作做服务端二次验证。

不要一次同时改模型、Prompt、RAG 和工具定义。否则即使效果改变，也很难判断真正起作用的因素。

## 6. 一套可重复的 Agent 调优闭环

我建议把持续优化流程固定成以下七步：

```text
1. 发现问题
      |
      v
2. 收集代表性 Trace / 用户反馈
      |
      v
3. 分类并定位根因
      |
      v
4. 提出一个可验证的优化假设
      |
      v
5. 在固定评测集上做对照实验
      |
      v
6. 小流量上线并观察线上指标
      |
      v
7. 沉淀失败样本，更新评测集和文档
      |
      +----------------------> 回到 1
```

### 6.1 把“我觉得不好”转换成问题假设

例如：

**模糊描述：** Agent 经常回答不准确。

**更具体的观察：** 在最近 100 条订单问题中，有 18 条回答引用了过期订单状态；其中 15 条 Trace 显示 Agent 没有调用实时订单查询工具。

**优化假设：** 对涉及订单实时状态的问题，应该优先调用订单查询工具；知识库只用于解释规则，不用于提供订单当前状态。

**实验方案：** 修改工具路由规则，在固定订单问题评测集上比较工具调用率、任务成功率、错误引用率、P95 延迟和成本。

**验收条件：** 错误引用率下降，任务成功率不下降，同时成本和延迟在预算范围内。

这样，优化过程就从“不断调 Prompt”变成了一次可复现的工程实验。

### 6.2 一次尽量只验证一个主要变量

Prompt、模型、工具描述、检索参数和编排逻辑之间存在关联，但在诊断阶段应该尽量一次验证一个主要变化。

例如：

- 先只修改工具描述，再跑同一评测集。
- 如果没有改善，检查工具 Schema 和参数上下文。
- 如果工具调用正确但答案仍然错，再检查工具返回和最终生成。

复杂问题可能需要组合调整，但每次实验都应该记录变更内容和预期作用，确保能够解释结果。

### 6.3 不只看平均分，也要看失败案例

一个版本的总体任务成功率提升了 3%，并不意味着所有用户都受益。它可能在常见问题上变好，却让某类高风险请求变得更差。

建议至少按以下维度分组：

- 任务类别和复杂度。
- 用户类型、权限和租户。
- 是否需要 RAG、工具调用或多轮上下文。
- 数据源和工具类型。
- 成功、失败、拒绝和人工接管。
- 高风险与普通任务。

优化应兼顾总体质量和关键分组的质量下限。

## 7. 工具与平台怎么选？

调优体系不一定需要一开始就采购一整套平台。可以从业务 Trace、固定评测数据集和简单报告开始，规模增长后再引入专用工具。

| 工具或方案 | 主要用途 | 适合情况 |
| --- | --- | --- |
| OpenTelemetry | 统一 Trace 和指标采集 | 希望减少对单一厂商的绑定 |
| [Arize Phoenix](https://phoenix.arize.com/) | Trace、数据集、实验和评估 | 希望自托管或开源方式做可观测性与评测 |
| [LangSmith](https://www.langchain.com/langsmith/evaluation) | Agent Trace、离线/线上评估和数据集 | 使用 LangChain/LangGraph，或需要托管评测流程 |
| OpenAI Agents SDK Tracing / Evals 工作流 | 观察 SDK 执行轨迹并评估 Agent 行为 | 主要使用 OpenAI Agents SDK 或相关平台能力 |
| 自建评测脚本 | 业务断言、工具轨迹、成本和回归 | 初期任务数量有限、验收规则较明确 |

平台可以提供 Trace UI、数据集、评测器和实验管理，但不能替你定义什么是业务上的成功。**最重要的资产是自己的真实评测样本、正确的质量标准和失败案例库。**

## 8. 调优中常见的误区

### 误区一：所有问题都通过追加 Prompt 解决

Prompt 可以改善指令表达，但无法修复错误的数据、缺失的权限校验、错误的业务 API 和不可靠的重试机制。

### 误区二：模型越强，Agent 就一定越好

更强模型可能提高复杂任务表现，但也可能增加成本和延迟。应该按任务做对照评测，而不是只看模型排行榜。

### 误区三：上下文越长越好

冗余历史和低相关资料可能增加成本并干扰模型。上下文工程的目标是提供高信号信息，不是尽可能多地提供信息。

### 误区四：给 Agent 更多工具，它就会更有能力

工具数量越多，选择空间和错误机会也越大。工具应该最小化、职责清晰、权限受控。

### 误区五：多 Agent 能解决单 Agent 的所有问题

如果问题来自数据不准确、工具定义差或业务约束不清，拆成多个 Agent 只会把问题分散到更多节点。

### 误区六：只看最终回答，不看执行过程

最终答案看起来合理，背后也可能发生过越权调用、错误查询或重复执行。对能产生真实业务影响的 Agent，必须检查完整 Trace 和业务状态。

### 误区七：一次上线后就算调优完成

模型、用户请求、外部数据、工具和业务规则都会变化。Agent 质量需要持续监控、定期评测和回归验证。

## 9. 一个轻量的持续优化模板

每次发现问题时，可以用下面的模板记录：

```markdown
# Agent Optimization Record

## 问题描述

- 发生频率与严重程度？

## 证据

- Agent / Prompt / Model 版本：

## 问题分类
- [ ] 意图理解
- [ ] 指令遵循
- [ ] RAG / 数据质量
```

## 结语

Agent 调优不是一门只靠经验写 Prompt 的手艺，而是一套建立在数据、观测、评测和工程控制之上的持续改进过程。

好的 Agent 并不是永远不出错，而是系统能够发现错误、解释错误、控制错误的影响，并把真实问题转化为下一轮可验证的优化。

对于开发者来说，最重要的能力不是记住某个模型的提示词技巧，而是建立一套稳定的方法：**观察真实行为、定位失败环节、提出清晰假设、用评测验证变化，再通过灰度发布确认收益。**

当 Agent 开始服务真实用户，调优就不再是上线前的一次性工作，而是产品和工程体系的一部分。
